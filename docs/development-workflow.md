# 🔁 VJAでのアプリ開発フロー: ウィザードから機能仕上げまでの一連の流れ

このドキュメントは、[プロジェクト新規作成ウィザード](sample-wizard-walkthrough.md)でプロジェクトの骨格を作った後、画面・DBテーブル・検証（バリデーション）・イベント処理を仕上げていくまでの**一連の開発フロー全体**を説明するものです。

個別の機能の詳しい使い方は[ユーザーガイド](user-guide.md)、1つの機能（ログイン・ユーザ登録）を実際に組み上げた具体例は[サンプルウォークスルー](sample-login-nocode.md)を参照してください。本ドキュメントは、それらの工程を**どういう順番で・どういう考え方で繋げていくか**という全体像に特化しています。

---

## 全体を貫く1つの考え方: 「生成 → 確認 → 必要なら直す → 次へ」

VJAのAI雛形生成機能（画面デザイン・DBテーブル・検証・イベント処理のいずれも）は、すべて次の同じサイクルで進みます。

1. **日本語で依頼文を書く**（またはウィザードの質問に答える）
2. **AIが雛形を生成する**（YAML/JSON/コード）
3. **内容を確認する**（想定通りか目を通す）
4. **直したい点があれば、依頼文を直して再生成する**（ゼロから書き直すのではなく、一言足す・直すだけで再生成できる）
5. 問題なければ次の工程へ進む

このサイクルを、プロジェクト全体の立ち上げ（ウィザード）から、画面1つ・DBテーブル1つ・イベント1つ・バリデーション1つの単位まで、**同じ考え方で繰り返し適用する**のがVJAの開発フローです。「白紙から要件を思い出しながら組み立てる」作業がほぼ発生せず、常に「既にある生成結果を見て、気になる点だけ直す」作業に置き換わります。

---

## 全体の工程

```
0. ウィザードでプロジェクト骨格を作る
        ↓
1. 生成されたフォーム・DBテーブル定義を確認・修正する
        ↓
2. 検証（バリデーション）をAI生成し、必要なら修正する
        ↓
3. 各イベント処理を「YAMLドラフト生成→(必要なら修正)→JS生成→(必要なら修正)」で作る
   （フォーム内の全イベントについてこのループを繰り返す）
        ↓
4. 実行して動作確認し、問題があれば該当する工程に戻って直す
```

### 0. ウィザードでプロジェクト骨格を作る

思いつきの日本語だけで、AIとのQ&Aヒアリングを経て「複数フォームの雛形＋DBテーブル候補（名前と説明のみ）」を一括生成します。詳しい流れは[ウィザードのウォークスルー](sample-wizard-walkthrough.md)を参照してください。

この時点でできるのは**画面の骨組みとテーブルの仮登録**のみで、DBのカラム構成・画面遷移・業務ロジック・入力チェックはまだ存在しません。次のステップ以降で1つずつ仕上げていきます。

### 1. 生成されたフォーム・DBテーブル定義を確認・修正する

**フォーム側**: ウィザードで生成された各フォームの画面デザインYAMLドラフト（「✨ YAMLドラフト」タブの依頼文）を確認し、足りない項目やボタンがあれば依頼文に一言追記して「✨ YAMLドラフト生成」→「🤖 画面反映」を再実行します。ウィジェットをコピペで増やすのではなく、**依頼文を直して再生成する**方が、複製元のイベントJSが誤って残るリスクも無く簡潔です（詳細は[ログイン・ユーザ登録サンプル](sample-login-nocode.md#1-画面デザインyamlドラフト生成)を参照）。画面の大まかな構成（入力・表示・ボタンの配置）で狙いと違う部分があれば、「🖼 レイアウト」タブでレイアウトイメージを選び直すこともできます。

**DBテーブル側**: テーブル管理の「✨ AI生成」で、テーブル名・説明（＋必要なら依頼文）からカラム構成（列名・型・NOT NULL・PK・インデックス・デフォルト値）を生成します。生成結果のカラム名・型が意図と違えば、依頼文を足すか、そのままカラム一覧を手で直しても構いません。

> 💡 この段階で画面とDBのカラム名が固まっていると、後続のイベントYAML生成・検証AI生成で、AIがそれらの名前を自動的にコンテキストとして参照してくれるため、以降の工程での手戻りが少なくなります。

### 2. 検証（バリデーション）をAI生成し、必要なら修正する

各フォームのバリデーション編集モーダルで、「定義名」と「説明」を記載し、「依頼文」を入力して「✨ AI生成」を実行します。

この時、フォームに配置済みの入力系ウィジェット名が自動的にAIへ渡されるため、実在するウィジェット名に対して正しくルールが割り当てられます。生成されたルール（対象ウィジェット・チェック種別・エラーメッセージ）を確認し、過不足があれば依頼文を直して再生成するか、ルール一覧を直接編集します。

生成した検証定義は、YAML表示でのプロパティから `検証: 定義名` を選択するだけで、対応するイベントJSの先頭に自動挿入されるため、次のイベント処理の工程を待たずに先に用意しておくことができます。

#### バリデーションAI生成例

ユーザ名、パスワードの検証を行う場合は「依頼文」に以下のように書くと良いです。
- ユーザ名はメールアドレス、パスワードは８文字以上で、必須入力で

 これによって「メールアドレス、パスワードのバリデーション設定が自動的に定義」されます。

### 3. 各イベント処理を作る（YAMLドラフト→修正→JS生成→修正のループ）

フォーム内のボタン・入力欄などのイベント（Click / TextChanged 等）ごとに、次の手順を繰り返します。

1. イベントYAMLエディタの「✨ YAMLドラフト」タブに、やりたいことを日本語で書く
2. 「✨ YAMLドラフト生成」で、YAML定義（説明/入力チェック/アクション/正常終了/エラー終了）のドラフトを作る
3. 生成されたYAMLを確認し、意図と違う部分があれば直接編集する（この時点ではまだJSコードにはなっていないので、修正コストが低い）
4. 「🤖 JSコード生成」でJavaScriptコードを生成する
5. VJAの自動検証（構文チェック・APIホワイトリスト・禁止パターン検出・モック実行スモークテスト）を通過するか確認する。問題があれば自動で1回だけAIに再修正を依頼する仕組みが働く
6. それでも動作が意図と違う場合は、YAMLドラフトの依頼文を直して2に戻る（同じ間違いを繰り返す場合は「🎲 ランダム性を上げて再生成」も使える）

このループを、フォーム内の全イベント（ボタン1つ1つ）に対して繰り返します。「YAMLの時点で直す」→「JSの時点で直す」という2段階の修正ポイントがあるため、いきなり長いJavaScriptコードを読んで直すよりも、修正の的を絞りやすいのがポイントです。

### 4. 実行して動作確認する

「▶ 実行」でアプリを動かし、実際の画面遷移・入力チェック・DB更新などを確認します。想定と違う挙動があれば、それがどの工程（画面レイアウト・DBカラム・検証ルール・イベントJS）に起因するかを判断し、該当する工程に戻って依頼文を直して再生成します。

## この流れで、人が行う作業はどれだけ減るのか

| 作業 | 従来（手作業） | VJAでの流れ |
|---|---|---|
| 画面構成の洗い出し | 要件を思い出しながら画面数・入力項目を設計 | ウィザードのQ&Aヒアリングに答えるだけ |
| ウィジェット配置・命名 | 1つ1つドラッグ配置し、名前を手入力 | 依頼文＋レイアウトイメージ選択からAIが自動生成 |
| DBテーブル設計 | カラム名・型・制約を1つずつ検討 | テーブル名・説明からAIがカラム構成を生成 |
| 入力チェック実装 | チェックロジックをコードで実装 | 依頼文からルール一覧をAI生成、YAMLに1行差し込むだけ |
| 業務ロジック（イベント処理） | SQL・エラーハンドリングを含むコードを1から実装 | YAMLドラフト→JS生成の2段階で、依頼文の追記・修正のみで作成 |

人が最後まで行う作業として残るのは、**「日本語で依頼文を書く」「生成結果を見て妥当かどうか判断する」「必要なら依頼文やYAMLを直す」**という部分です。コードそのものを一から書く工程は、通常の開発フローではほぼ発生しません。

一方で、[ログイン・ユーザ登録サンプル](sample-login-nocode.md#まとめ)でも触れている通り、AIは依頼文に忠実に実装するため、**セキュリティ要件や業務ルールの妥当性を判断するのは人間の役割**です。「生成されたものを読んで判断する」というステップ自体は、工程を重ねても省略できません。

---

## まとめ

VJAの開発フローは、「ウィザードで骨格を作る」→「画面・DBを整える」→「検証を用意する」→「イベントごとにYAML→JSを積み上げる」という工程を、**すべて同じ『生成→確認→必要なら直す』というサイクルの繰り返し**として統一的に扱えるように設計されています。工程が変わっても操作の型が変わらないため、覚えることは少なく、慣れるほど早くアプリを組み上げられるようになります。
