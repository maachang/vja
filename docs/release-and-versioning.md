# 📦 リリースとバージョン管理の方針（検討メモ）

> **状況: 検討段階（未実施）**。ある程度の機能が担保できた段階でリリースを行い、各プラットフォーム向けの実行アーカイブを配布する予定です。本ドキュメントは、その時に迷わないよう、現状の確認結果と方針案、決めるべき事項を整理したものです。実際に運用を始める際に、内容を見直して確定させます。

---

## 1. 現状（確認済みの事実）

- **バージョンの元**: `package.json` の `version`（現在 `0.1.0`）が唯一の元です。`electrobun.config.ts` が起動時にこの値を読み、アプリのバージョンとして使います。
- **ビルド**: `bun run build`（内部では `electrobun build --env=stable`）を実行すると、`artifacts/` ディレクトリに、プラットフォームごとの成果物が出力されます。`artifacts/` は `.gitignore` 済みで、Git の管理対象ではありません。

  | ファイル（Linux x64 の例） | 役割 |
  |---|---|
  | `stable-linux-x64-vja-Setup.tar.gz` | インストーラー（約35MB） |
  | `stable-linux-x64-vja.tar.zst` | 更新用の本体アーカイブ（約35MB） |
  | `stable-linux-x64-update.json` | 更新情報（`version`・`hash`・`platform`・`arch`） |

- **更新の仕組み（Electrobun 側）**: Electrobun は、`baseUrl` で指定した場所から、`…-update.json`、差分パッチ（`.patch`）、本体の tarball を取得する作りです。つまり、**更新用のファイル一式を、HTTP で取得できる場所に置く**ことが前提です。
- **固定している依存**: Electrobun は `1.18.1` に完全固定し、同梱の bun を 1.4.2 に差し替え、パッチ（`patches/`）を適用しています。詳細は開発者向けの内部ノートにまとめています。リリース物の再現性に直結するため、リリース手順には「同じ依存で再現できるか」の確認を含めます。

## 2. 方針案

### 2.1 ソースと成果物は分けて管理する

| 対象 | 置き場所 | 理由 |
|---|---|---|
| ソースコード | Git（タグでバージョンを付ける） | 履歴・差分管理に向く |
| ビルド成果物（`artifacts/` の中身） | GitHub Releases の添付ファイル | 1ビルドが約70MB（Setup と本体）あり、Git の履歴に入れるとリポジトリが肥大化するため |

- バージョンごとに Releases が残るので、過去の版もいつでも取得できます。ダウンロード URL もバージョンで固定されます。
- Windows / macOS / Linux の成果物は、同じ Release に並べます。

### 2.2 バージョン番号

- `package.json` の `version` を**唯一の元**にします（現状のままです）。
- 形式は `MAJOR.MINOR.PATCH`（セマンティックバージョニング）を基本にします。
  - 機能が固まるまでは 0.x（`0.1.0` → `0.2.0` …）とし、安定したと判断した時点で `1.0.0` とします。
  - バグ修正のみは PATCH、機能追加は MINOR、互換性を壊す変更は MAJOR を上げます。
- Git のタグは `v0.1.0` の形式にし、`package.json` の version と必ず一致させます。

### 2.3 リリース手順（案）

1. 変更をすべてコミットし、`bun test` が通ることを確認する
2. `package.json` の `version` を上げ、コミットする
3. 同じ版を Git のタグ（`vX.Y.Z`）として打つ
4. 各プラットフォームで `bun run build` を実行し、`artifacts/` の成果物を得る
5. GitHub Releases にタグと同名の Release を作り、成果物を添付する（変更点をリリースノートに書く）
6. 公開前に、成果物から実際にインストール・起動できることを確認する

> 手順は、最初は手順書として運用し、回数を重ねて安定した段階でスクリプト化（または CI 化）する、という進め方を想定しています。

### 2.3.1 プラットフォームごとの確認事項

- **Windows**: アイコンの埋め込みは、ビルド後のフック（`scripts/win-embed-icon.ts`）で回避しています。リリースビルドでもフックが動き、アイコンが付いていることを確認します。
- **macOS**: ビルドは macOS 上で行う必要があります（アイコン変換に `iconutil` を使うため）。配布する場合は、Apple の署名・公証をどうするかが論点になります（現状は開発時の署名の扱いのみ）。
- **Linux**: 成果物は `tar.gz` / `tar.zst` 形式です。必要な共有ライブラリが、配布先の環境に入っているかを確認します。

### 2.4 自動更新

- Electrobun の更新機構を使う場合は、`baseUrl` に、成果物を置いた場所の URL を指定する構成になります。GitHub Releases に置く案が第一候補です。
- ただし、次の点は**未検証**です。
  - GitHub Releases の URL 構造で、Electrobun が期待するファイル名・パスの規則に合わせられるか
  - 「最新版」を指す固定 URL が使えるか（使えない場合は、更新情報だけ別の場所に置く必要があります）
  - 差分パッチ（`.patch`）が、複数プラットフォームで正しく動くか
- 最初から自動更新を入れる必要はありません。**最初は「Releases から手動でダウンロードして入れ替える」運用**でも十分で、自動更新は、運用が安定してから追加できます。

## 3. VJA 固有の論点

### 3.1 vja 本体と、vja で作ったアプリは別のバージョン

- VJA の「コンパイル」機能で作られたアプリ（ユーザーが作るアプリ）は、vja 本体とは独立した配布物です。
- ユーザーのアプリにも、バージョン管理や更新の仕組みを持たせるかは、**要件として決める必要があります**。持たせる場合は、プロジェクトの情報（`projectInfo`）にバージョンを保持する案が考えられます。
- コンパイルされたアプリは、同梱する Electrobun・bun のバージョンやパッチを、vja 本体と共有しています。vja 本体の依存を更新したときは、コンパイル側にも影響するため、両方を確認します。

### 3.2 依存バージョンの扱い

- Electrobun は最新版への追従が危険なことがわかっています（特定のバージョンで起動不能になった事例があります）。バージョンを上げるときは、**起動確認を必ず行ってから**採用します。
- bun のバージョンを上げる場合も、Electrobun との組み合わせの動作確認が必要です。

## 4. 決めておくべきこと

| # | 論点 | 選択肢の例 |
|---|---|---|
| 1 | 配布場所 | GitHub Releases（公開／非公開）、自前のサーバー、その他 |
| 2 | 自動更新を入れるか | 最初は手動ダウンロード → 安定後に追加／最初から入れる |
| 3 | ユーザーのアプリ（コンパイル成果物）にバージョン・更新の仕組みを持たせるか | 持たせない／プロジェクトにバージョンを持たせる／更新機構も用意する |
| 4 | リリース手順の運用 | 手順書で運用／スクリプト化／CI で自動化 |
| 5 | macOS の署名・公証 | 行わない（利用者が個別に許可）／Apple の署名・公証を行う |
| 6 | バージョンの付け方 | 0.x のうちは MINOR で機能追加、1.0.0 の基準を決める |

---

## 5. 試作（実装前の検証）の進め方

本番の運用に入る前に、小さな検証を行うことを想定しています。

1. テスト用のタグ（例: `v0.0.1-test`）で、1つのプラットフォームの成果物を作り、GitHub Releases にアップロードする
2. Electrobun の `baseUrl` をその Release の URL に向け、更新情報の取得・本体の取得が動くかを確認する
3. 動かない場合は、ファイルの置き方・名前を、Electrobun の命名規則（`naming.ts` の URL 生成）に合わせる
4. 古い版からの更新（0.0.1 → 0.0.2 など）が成功することを確認する
