# 申請・承認ワークフロー系

## 概要
「経費申請」「休暇申請」のように、1件のデータが申請→承認/却下というステータスを遷移していく業務の骨格。

## テーブル構成の型
単一テーブルにステータス列を持たせる形が基本形。

```
例: 経費申請
- expense_requests
  - id            INTEGER PRIMARY KEY
  - applicant     TEXT NOT NULL     -- 申請者名
  - amount        REAL NOT NULL     -- 申請金額
  - reason        TEXT              -- 申請理由
  - status        TEXT NOT NULL     -- "pending"（申請中） / "approved"（承認） / "rejected"（却下）
  - appliedAt     TEXT NOT NULL     -- 申請日時
  - reviewedAt    TEXT              -- 承認/却下日時
  - reviewComment TEXT              -- 承認者コメント
```

## 画面構成の骨格（重要）
- **申請一覧画面（1つ）**: 自分の申請の一覧＋ステータスの色分け表示。新規申請ボタンから登録フォームを開く（同一画面内のモーダル等）
- **承認一覧画面（1つ）**: 「申請中」のみを一覧表示し、行から詳細を開いて承認/却下ボタンを操作できるようにする。承認・却下も専用の別画面を作らず、詳細表示と同じ画面内のボタンで完結させる
- ステータスの選択肢はselectBoxの固定itemsで十分（頻繁に増減しないため）

## AIが陥りやすい失敗（回避したい点）
- 「申請画面」「承認画面」「却下画面」「申請詳細画面」を別々のFormとして量産してしまう（承認/却下は詳細表示画面のボタン操作で十分）
- ステータスの選択肢を自由入力のtextにしてしまい、表記ゆれが発生する実装にする
- 承認済み・却下済みのデータを編集可能なままにしてしまう（ステータスに応じて編集不可にする配慮が必要）
