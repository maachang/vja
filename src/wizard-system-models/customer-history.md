# 会員・対応履歴管理系

## 概要
顧客・会員のような対象マスタに対し、対応履歴・問い合わせ内容が時系列で1対多に積み上がっていく業務の骨格。CRM（顧客関係管理）的なアプリの中心パターン。

## テーブル構成の型
対象マスタ＋履歴テーブルの2テーブル構成が基本形。

```
例: 顧客対応履歴
- customers (顧客マスタ)
  - id            INTEGER PRIMARY KEY
  - name          TEXT NOT NULL
  - contact       TEXT              -- 連絡先

- contact_logs (対応履歴)
  - id            INTEGER PRIMARY KEY
  - customerId    INTEGER NOT NULL  -- customersへの参照
  - contactedAt   TEXT NOT NULL     -- 対応日時
  - channel       TEXT              -- 対応手段（電話/メール/訪問等、selectBox）
  - content       TEXT NOT NULL     -- 対応内容
  - staffName     TEXT              -- 対応者名
```

## 画面構成の骨格（重要）
- **顧客一覧画面（1つ）**: 顧客名等で検索し一覧表示。行をクリックすると詳細画面へ
- **顧客詳細画面（1つ）**: 顧客の基本情報＋対応履歴の時系列一覧（datagridまたはリスト表示）を**同一画面内**にまとめる。この画面内に「対応履歴を追加」フォームも配置し、別画面に飛ばさない
- 顧客自体の登録・編集は、マスタ管理系と同じ考え方（別画面ではなくモーダル等で完結）

## AIが陥りやすい失敗（回避したい点）
- 顧客情報の画面と対応履歴の画面を完全に分離し、行き来が煩雑なUIにしてしまう
- 履歴を新しい順に並べず、追加した順のまま表示してしまう（時系列確認が目的なので新しい順表示が基本）
- 「対応履歴一覧画面」「対応履歴登録画面」を顧客詳細画面と別に作ってしまう
