# マスタ管理系

## 概要
「商品」「顧客」「社員」のような、業務上繰り返し参照される単一エンティティを、登録・一覧・検索・更新・削除する最も基本的な骨格。VJAで作るアプリの中で最も出現頻度が高いパターン。

## テーブル構成の型
1テーブルで完結させるのが基本形。

```
例: 商品マスタ (products)
- id            INTEGER PRIMARY KEY
- code          TEXT NOT NULL   -- 商品コード（表示・検索用）
- name          TEXT NOT NULL   -- 商品名
- category      TEXT            -- 分類（selectBoxで選択させる想定）
- price         REAL            -- 単価
- stock         INTEGER         -- 在庫数（必要な場合のみ）
- note          TEXT            -- 備考
- updatedAt     TEXT            -- 更新日時
```

区分値（categoryのような固定選択肢）は、別テーブルに切り出すか、selectBoxの固定itemsで持たせるかを、選択肢の変動頻度で判断する（頻繁に増減する→別テーブル、ほぼ固定→items）。

## 画面構成の骨格（重要）
**一覧・登録・編集・削除・詳細表示を、安易に別画面へ分割しないこと。** 人間の開発者は通常、次のように統合する。

- **メイン画面（1つ）**: 検索条件（コード・名称等でのあいまい検索）＋一覧表示（datagrid）
- 一覧の行をクリック、または「＋新規」ボタンで、**同一画面内のフォーム領域（または1つの登録/編集モーダル）** を開き、新規登録・編集を1つのUIで兼用する
- 削除は一覧の行に削除ボタンを置くか、登録/編集画面内に削除ボタンを置く（確認ダイアログ`vja.app.showConfirm`必須）。**削除専用の別画面は作らない**
- 詳細表示が必要な場合も、基本は編集画面をそのまま流用する（読み取り専用モードの別画面は原則不要）

## AIが陥りやすい失敗（回避したい点）
- 「一覧画面」「登録画面」「編集画面」「削除確認画面」「詳細画面」を5つの別Form/別画面として作ってしまう → 上記の通り1〜2画面に集約する
- 検索条件を用意せず、全件一覧のみにしてしまう（データ件数が増えると実用にならない）
